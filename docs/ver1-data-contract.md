# Ver.1 데이터 계약 — 검토 초안

작성일: 2026-10-20 (Asia/Seoul)  
상태: **명세 검토 중 / Cafe24 접근 미확인·승인 대기 / 연동 구현 미착수**

이 문서는 [제품 계획](product-plan.md)의 Ver.1을 구체화하는 내부 계약 후보다. API 명세, 실행 DTO, DB 스키마 또는 실제 데이터 수집 승인이 아니다. 매출 정책은 [매출 지표 명세](ver1-sales-metrics.md)를 함께 검토한다.

후속 요청으로 [로컬 화면 초안과 공식몰 공개 카탈로그](ver1-preview.md)를 구현했다. 아래 문서 한정 결정은 최초 명세 작업의 범위이며, 실제 고객·주문 연동 승인은 계속 대기 중이다.

## 2. 공통 표현과 원천 매핑

아래 이름은 내부 논리 필드이며 Cafe24 필드명이 아니다. 실제 엔드포인트·권한 scope·상태 코드는 아직 확인하지 않았다. **모든 필드의 원천 매핑은 확인 필요**이며, 승인된 공식 API 명세 또는 비식별 내보내기 열 명세를 확보한 뒤 채운다.

- ID: 원문을 보존하는 문자열. 숫자로 변환해 선행 0을 제거하지 않는다. 원천 시스템·몰·채널별 ID 유일성 범위를 확인한다.
- 금액: 원 단위 정수. 원천의 세금·할인 포함 여부와 부호를 확인하고 매핑한다. KRW 이외 통화는 환율을 가정하지 않고 별도 검토한다.
- 수량: 정수 후보. 비정수 수량이 발견되면 임의 반올림하지 않고 계약 변경을 검토한다.
- 시각: 원천 시간대·정밀도와 함께 해석해 UTC로 정규화한다. 시간대 없는 값은 KST로 추정하지 않는다. 날짜만 있으면 시각을 만들어 넣지 않는다.
- `필수`: 해당 데이터의 검증·집계에 필요한 값. `조건부`: 해당 사건·기능이 존재할 때 필요. `선택`: 제공·수집 승인 범위 안에서만 사용.
- 미제공·미상·해당 없음·실제 0을 구분한다. 누락을 0, false, 가짜 ID로 대체하지 않는다. 해당 없음으로 확정된 항목만 그 근거를 기록한다.

원천 매핑 승인표에는 다음을 필드마다 기록한다.

| 논리 필드 | 원천 문서 버전·열/필드 경로 | 정의·단위·상태 코드 | 변환·시간대 | 제공 범위·누락 의미 | 검토자·승인일·근거 |
|---|---|---|---|---|---|
| 아래 필드 각각 | 확인 필요 | 확인 필요 | 확인 필요 | 확인 필요 | 미지정·승인 대기 |

주문 수준의 배송비·결제 총액을 항목마다 복제 합산하지 않는다. 분할 결제·재결제와 주문·항목 ID의 관계, 할인 중복 여부, 구매 당시 금액의 정의는 원천 명세로 확인한다.

## 3. 검증·재수집 요구사항 — 제안

1. 승인 범위·계약 버전·원천 상태 매핑을 검증한 뒤 집계한다. 필수값 오류·알 수 없는 코드·애매한 연결은 격리하고 영향 기간·지표를 표시한다.
2. 원천별 안정적인 식별자로 재실행 중복을 방지한다. 같은 사건의 상태 변경과 별개의 부분 환불을 구분하며 배치 ID만으로 거래 중복을 판단하지 않는다.
3. 취소와 환불이 같은 경제 사건인지 연결해 두 번 차감하지 않는다. 원천의 사건 관계 확인 전 임의 규칙을 구현하지 않는다.
4. 지연 도착한 환불도 수집일이 아닌 환불 완료일에 귀속한다. 영향 기간의 최신 집계·재집계 시각을 표시한다. 원결제일은 환불로 재작성하지 않는다.
5. 원천 수정 이력·삭제 신호·안정적인 이벤트 ID가 없으면 재현성 한계와 재조회·수동 대사 절차를 문서화하고 승인받는다. 원천 오류 정정 정책은 별도다.
6. 격리 행이 있는 배치는 전체 성공으로 표시하지 않는다. 문제없는 범위의 잠정 합계를 보여주더라도 누락 범위와 대사 미완료를 함께 표시한다.
7. 원본 개인정보 행·연락처·자격증명은 로그·저장소에 남기지 않는다. 격리 데이터 자체의 저장 위치·최소 항목·접근 역할·보관 기간도 승인 전 미정이다.

| 사업 권한·약관·수집 목적 | 승인권자, 허용 목적·데이터 종류·이용 조건 | 담당자 미지정·승인 대기 |
| API 또는 공식 내보내기 | 승인된 앱/조회 권한 또는 내보내기 담당자·전달 방식 | 방법 미확인·승인 대기 |
| 실제 필드·상태 매핑 | 공식 명세 버전 또는 비식별 열 명세, ID·결제·환불 의미 | 자료 미확보 |
| 역사·누락·수정 | 이용 가능한 시작일, 채널, 지연·수정·삭제 이력, 조회 제한 | 확인 필요 |
| 매출 정책·관리자 대사 | 매출 명세 결정별 승인, 관리자 화면·필터·기준 시각·허용 오차 | 승인 대기 |
| 개인정보·직원 역할 | 최소 수집, 원본/집계/내보내기 역할, 보관·삭제·감사 책임 | 담당자 미지정·승인 대기 |
| 운영 환경·자격증명 | 환경·호스팅 지역·비밀 관리·권한 관리·보관 및 복구 책임 | 승인 대기 |

확인되지 않은 항목을 코드 기본값으로 확정하지 않는다. 필요한 접근·매출 정책·개인정보 승인이 기록된 범위에서만 후속 구현을 시작한다. 승인된 데이터 접근도 SOLAPI 발송이나 Gemini 고객 데이터 전송 승인을 의미하지 않는다.

## 5. 승인 후 구현·인수 조건

- `api/routers -> services -> stores`를 유지하고 런타임 SQL/DB 접근은 stores에만 둔다. Streamlit은 repository를 통해서만 백엔드를 호출하고 shared에는 transport·DTO만 둔다.
- 직원 인증·역할 검토와 고객 식별 모델을 먼저 확정한다. 외부 제공자는 작은 인터페이스와 fake로 검증하며 실서비스 테스트는 명시적 opt-in·자격증명 조건을 둔다.
- 아래 명세 검토 시나리오와 [매출 검증 시나리오](ver1-sales-metrics.md#5-검증과-관리자-대사)를 승인된 비식별 예제로 확인한다. 실제 관리자 대사는 접근 승인 후 수행한다.
- 구현 변경 후 `uv run pytest`, `uv run ruff check .`, `uv run mypy`를 실행한다. 마이그레이션이 필요하면 별도 추가형 변경과 rollback/forward-fix 계획을 검토한다.

| 시나리오 | 기대 결과 |
|---|---|
| 동일 배치·거래 재수집 | 주문·항목·환불 건수와 금액이 중복 증가하지 않음 |
| 두 번의 부분 환불·상태 변경 | 별개 사건은 각각 반영, 동일 사건 진행→완료는 한 번 반영 |
| 상품/고객 연결 불명확·알 수 없는 상태 | 자동 병합 없이 격리·영향 지표·기간 표시 |
| 결제일·구매 단가·환불 완료일 누락 | 해당 지표 계산 보류, 0·현재 가격·수집 시각으로 대체하지 않음 |
| 원천 수정 이력 미지원 | 재현성 한계와 미승인 복구 절차 명시 |
| 실제 비회원·동의 미상 | 가짜 고객 생성 금지, 동의 미상을 동의로 해석하지 않음 |

현재 인수 상태: **문서 초안 작성, 업무 승인·원천 매핑·관리자 대사 미완료.**
