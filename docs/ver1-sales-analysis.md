# Ver.1 매출 분석 화면과 더미 입력 계약

요청일: 2026-10-20 (Asia/Seoul). 사용자 메시지에서 취소선처럼 보인 부분을 포함해 구현했다. 현재는 공개 카탈로그·가상 데이터용 로컬 초안이며 실제 매출 정책·Cafe24/Supabase 운영 연동 승인은 대기 중이다.

## 화면 구성

로그인 후 사이드바의 기본 메뉴는 **매출 분석**이다.

1. **매출 요약**: 조회기간 순상품매출, 종료일 기준 월 매출·일 매출, 결제 주문 수, 결제 시점 평균 상품 주문금액, 구매 고객, 상품 환불, 기간 내 반복 구매 고객, 직전 동일 길이 기간 비교, 월별·일별 매출, 상품별 순매출 Top 120.
2. **매출 추이**: 기본 시작일 2020-01-01, 일 매출·20/30/365일 이동평균, 월별·연도별 합계, 1일·7일·30일 급변 알림, 주문금액대·고객별 평균 주문금액대 분포.
3. **고객별 매출 추이**: 남성·여성·미상, 10대~80대·10대 미만·90대 이상·미상 필터, 연령/성별 매출과 월별 추이, 구매 행동 고객군과 해당 고객군 상품 순위.

기존 상품·용량/EAN·리뷰·AI 화면은 **상품·리뷰·AI** 메뉴에 보존했다. 상품 가격·이전 공개 가격 관측은 수정하지 않았다.

분석 데이터는 실제 실적 연동 대기 / 기존 가상 실적 / 업로드 더미 데이터 중 선택한다. 기존 가상 실적은 2026-09-06~2026-10-20만 제공하며 성별·연령이 없어 미상이다. 2020년부터 실적이 있었다고 만들지 않는다. 업로드 파일에서 선언한 완전 이력 범위 밖은 빈 값이며, 부분 기간 합계는 제공 이력만 포함한다고 표시한다. 선언 범위 안의 무거래일만 0으로 집계한다.

카탈로그는 현재 116개다. Top 120은 거래에 등장한 상품을 순매출 내림차순, 동률 상품 ID 순으로 최대 120개 표시하며 임의 상품·실적을 채우지 않는다.

## 데모 지표 정의

- 결제 상품금액 = 구매 시점 수량 × 단가 − 항목 할인. 순상품매출 = 기간 결제 상품금액 − 기간 내 완료 상품 환불. 배송비와 배송비 환불은 별도다. 취소/미결제 주문을 넣는 계약이 아니며 결제가 확인된 주문만 입력한다.
- 기준일 일매출은 조회 종료일의 순상품매출, 기준월 매출은 해당 월 1일부터 종료일까지다. 월 1일부터의 완전 이력이 없으면 월 매출은 표시하지 않는다. 일·월 지표도 선택 고객군 필터를 따른다.
- 평균 상품 주문금액 = 선택 기간 결제 상품금액 / 고유 결제 주문 수. 환불·배송비는 분리한다. 회계상 AOV 최종 확정이 아니라 분포와 결제 행동 확인용 데모 지표다. 분모 0은 데이터 없음이다.
- 주문금액대: 3만원 미만 / 3만원 이상 5만원 미만 / 5만원 이상 10만원 미만 / 10만원 이상 20만원 미만 / 20만원 이상. 한 주문의 모든 항목을 먼저 합산한다. 고객별 평균 금액대는 고객별 주문 평균을 같은 구간으로 묶는다.
- 이동평균은 후행 단순 일평균이다. 단기 20일, 월 30일, 연 365일(달력 월/연 단위 평균을 뜻하지 않음). 무거래일 0 포함, 조회 시작일 이전의 제공 이력도 사용한다. 해당 일수의 완전 이력이 없으면 평균은 빈 값이다. 365일은 윤년의 달력 1년과 구분한다.
- 급변은 조회 종료일을 끝으로 최근 1/7/30일과 직전 동일 길이 구간을 비교한다. 조회 시작일과 독립된 종료일 기준 알림이며, 두 구간 모두 완전 이력이 필요하다. 기본 조건은 절대 증감액 100,000원 이상이면서 절대 증감률 50% 이상. 화면에서 조정한다.
- 기준 매출이 0 또는 음수이면 비율을 나누지 않고 증감액 조건으로 특이사항을 표시한다. 같은 금액이면 알림하지 않는다. 기간·상승/하락별 절대 증감액 순 최대 5개, 상품별 최근/직전 금액·차이·비율 또는 비율 불가 사유·일별 그래프와 표를 제공한다. 통계적 유의성이나 원인을 주장하지 않는다.
- 연령은 직접 제공된 출생연도와 구매연도의 차이인 연나이이며 만 나이가 아니다. 환불은 원구매 시점의 고객·연령대에 귀속한다. 출생연도·성별 미제공은 미상이고 이름·상품·리뷰로 추정하지 않는다.
- 고객군: 관측 첫 구매가 조회 기간 안인 신규 / 그 이전인 이전 구매 / 종료일까지 2회 이상 주문 / 평균 상품 주문금액 10만원 이상 / 할인 이용 / 한 주문에 3개 이상 구매. 관측 이력의 범위에 의존하며 조건 간 중복될 수 있다. 피부 상태·성격·고민·구매 동기를 추론하지 않는다.
- 세부 고객군 기여 고객이 5명 미만이면 금액·상품별 금액·선택군 추이를 숨긴다. 연령·성별 및 월별 세부 그룹도 같은 최소 표본 기준을 적용한다. 고객 상세·이름·전화번호는 출력하지 않는다.

## 향후 1,000건 입력 방법

각 매출 화면의 **더미 데이터 연결 · JSON 형식과 업로드**에서 예제 다운로드와 업로드를 제공한다. 이 계약을 따라 고객·주문 1,000건을 생성하면 별도 화면 코드 수정 없이 분석한다. 임의 형식의 파일을 자동으로 추측해 해석하지 않는다. 이번 작업에서는 실제 화면용 1,000건을 만들거나 저장하지 않았고 테스트에서만 생성해 검증했다.

```json
{
  "schema_version": "1",
  "synthetic": true,
  "coverage_start": "2020-01-01",
  "coverage_end": "2020-12-31",
  "customers": [
    {"customer_id": "dummy-customer-1", "gender": "female", "birth_year": 1990}
  ],
  "orders": [
    {
      "order_id": "dummy-order-1",
      "customer_id": "dummy-customer-1",
      "paid_on": "2020-01-15",
      "shipping": 3000,
      "items": [
        {"item_id": "dummy-item-1", "product_id": "11", "quantity": 1, "unit_price": 50000, "discount": 5000}
      ]
    }
  ],
  "refunds": [
    {"refund_id": "dummy-refund-1", "order_id": "dummy-order-1", "item_id": "dummy-item-1",
     "completed_on": "2020-02-01", "quantity": 0, "amount": 10000, "shipping_refund": 0}
  ]
}
```

- 고객/주문/항목/환불 ID는 `dummy-`로 시작하고 뒤에 영문·숫자·`_`·`-`만 허용한다. 상품 ID는 현재 공개 카탈로그의 문자열 숫자 ID를 사용한다. EAN이나 이름으로 임의 매칭하지 않는다.
- 고객 `gender`는 `male`, `female`, `unknown`, 생략 시 `unknown`. `birth_year`는 정수 또는 null, 생략 시 null. 입력하지 않은 정보를 추측하지 않는다. 이름·연락처 등 계약 외 필드는 거절한다.
- `paid_on`과 `completed_on`은 Asia/Seoul 영업일 `YYYY-MM-DD`다. 날짜만 있는 가상 사건에 UTC 시각을 만들어 넣지 않는다. 향후 실제 사건 API에서는 승인된 UTC 시각과 KST 영업일로 매핑한다.
- 모든 금액은 부동소수점이 아닌 0 이상 정수 KRW. `unit_price`는 구매 당시 할인 전 단가, `discount`는 해당 항목의 총 할인액이다. 주문 할인은 승인된 배분 후 항목 할인에 포함해 넣는다. 배송비는 주문마다 한 번만 입력한다. 공개 표시 가격으로 과거 거래 금액을 재계산하지 않는다.
- `refunds`는 생략 가능하다. 환불 `amount`는 원항목에 대한 할인 후 상품금액 환불이며 `shipping_refund`와 구분한다. 완료된 증분 사건만 입력하고 누적 환불 스냅샷을 각 사건 금액으로 반복 입력하지 않는다. 원거래 참조·결제일 이후·누적 환불금액/수량/배송비 상한을 검증한다.
- `coverage_start/end`는 해당 범위의 이력이 완전하다는 가상 데이터 생성자의 선언이다. 수집 실패·누락 기간을 완전하다고 표시하면 안 된다. 2020-01-01 이전·미래 이력은 거절한다. 고객·주문 ID 중복, 고객/상품/항목 연결 누락, 과도 할인·환불은 거절하며 기존 파일은 유지한다.
- 전체 스냅샷을 검증 후 교체한다. 덧붙이기 방식이 아니므로 같은 파일을 반복 업로드해도 매출이 중복 합산되지 않는다. 바이트 일치 재입력은 `unchanged`로 반환한다. UI 업로드 한도 8MB, 고객·주문 각 10,000개, 주문 항목 최대 20개, 전체 항목 최대 100,000개, 환불 20,000개다.
- 연결 성공 후 데이터 소스와 세 페이지의 조회 기간이 업로드 이력 범위로 바뀐다. 서버 재시작 후에도 로컬 store에서 읽는다. 저장 파일은 `.local/sales_dummy.json`이며 `.gitignore`로 제외한다. 실제 고객·주문 데이터 저장소로 사용하지 않는다.

## API·계층·검증

- GET `/api/v1/sales/preview`: source=pending/demo/dummy, start/end, gender, age, persona, alert_percent, min_change. 2020-01-01~KST 오늘까지만 조회한다.
- POST `/api/v1/sales/dummy`: 위 전체 JSON 스냅샷. 검증 완료 후 교체하고 고객/주문/항목 건수·데이터 해시·imported/unchanged 상태 반환.
- GET `/api/v1/sales/dummy/schema`: 생성기에서 사용할 JSON Schema.
- FastAPI router → 매출·입력 검증 service → store 방향을 유지한다. SQL/DB 추가 없음. 로컬 합성 데이터의 파일 저장도 store에 한정한다. Streamlit은 sales repository와 shared DTO/transport만 사용한다.
- 입력·집계·화면에는 실제 인증·역할·Supabase 연동을 연결하지 않았다. 현재 UI 데모 로그인은 실제 API 보안이 아니다. API는 로컬 공개 카탈로그·합성 데이터 전용이며 실제 데이터 전환 전에 인증·역할·RLS·보관 정책·매출 정책 승인이 필요하다.
- 검증: 1,000명·1,000주문/항목 JSON 입력과 중복 재입력, 저장 후 재로드, 잘못된 연결의 기존 데이터 보존, 일/월/연/상품 매출 대사, 20/30/365일 예열·이전 이력·빈 기간, 환불 완료일, 알림 상승/하락 최대 5개·0 기준, 성별/연령/행동 필터·소표본 숨김, 세 화면 렌더링과 기존 기능 회귀.
- 결과: pytest 28 passed, Ruff 통과, mypy 39개 소스 파일 통과. 작업공간 uv 캐시·offline/no-sync 옵션 사용. 실제 로컬 API를 호출한 별도 AppTest에서도 로그인 후 세 페이지와 기존 상품 116개 화면이 정상이며, 더미 원장 미생성·공개 가격 파일 해시 불변 확인. 기존 테스트 종료 임시 디렉터리 정리 권한 경고는 별개 환경 제한이다.

복구: sales router 등록·사이드바 분기·새 매출 모듈을 이전 상태로 복원하고 Streamlit 재시작. `.local` 더미 파일은 분석 연결에서 제외하거나 이전 파일로 복원한다. DB·운영 마이그레이션·메시지 발송·커밋은 없다.
